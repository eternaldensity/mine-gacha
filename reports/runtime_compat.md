## Probe sequence

Repeat this after any pack change; the record above covers one archive only. It is the only step that produces new runtime evidence.

1. `java -version` reports 21 or newer.
2. Install the `.mrpack` from `dist/` into a throwaway instance, not a long-lived one.
3. Start a dedicated server with 4-6 GiB, wait for `Done`, then stop it cleanly.
4. Join with one client; open a chest, a quest and one tech GUI.
5. Capture `logs/latest.log`, `logs/debug.log` and any `crash-*.txt` into `data/runtime/logs/`.
6. Run `python3 -m chaoslab runtime --log data/runtime/logs` and triage the findings, including the build-identity verdict.

## Build identity

A triage run compares every jar NeoForge reports discovering under the instance `mods` folder against the `filename` values pinned in `pack_lock.json`. The launcher framework jars NeoForge also discovers (`client-*-srg.jar`, `neoforge-*-universal.jar`) are ignored because they are not pack content. A capture that lists an unlocked jar or omits a locked one is `drift` and fails the run; a capture with no discovery lines is `unverified` rather than a pass, because truncated evidence cannot identify the build. Filenames are the strongest signal a log carries: a same-named jar re-uploaded with different bytes is indistinguishable without the lock hashes.

## Conflict taxonomy

| Kind | Severity | Action |
| --- | --- | --- |
| missing-dependency | critical | Add the requested dependency, or exclude the requester in `pack_manifest.json`. A required dependency outside the pack is a hard stop. |
| duplicate-mod | critical | Remove one of the duplicated jars; the lock must name exactly one build per project. |
| mixin-failure | critical | Pin the mixin owner and the target to versions known to build together, or drop one. |
| registry-conflict | high | Two projects claim the same registry key; pin versions or drop one of them. |
| client-class-on-server | high | Move the project to client-only (server-unsupported) or drop it from the server. |
| class-loading | high | Usually a missing mandatory dependency or a client class on a server; cross-check the side audit above. |
| out-of-memory | high | Environment, not a mod conflict: raise -Xmx and re-run before blaming a project. |
| worldgen-conflict | medium | Pin the biome/feature providers or drop one worldgen project; compare against the worldgen survivors in the manifest. |
| datapack-error | medium | Identify the namespace in the evidence line, then pin or drop that project. |
| fatal-crash | critical | Use the top project in the crash report as the suspect; remove or pin it and re-run. |
| crash-report | critical | Treat the description and the first project in the stack as the suspect. |

## Finding and removing a conflict

1. Reproduce: the same failure must occur twice from a clean instance before it counts.
2. Capture: keep the full log and crash report; do not truncate the first 200 lines.
3. Classify: run the harness. When no rule matches it says so instead of guessing.
4. Isolate: remove half the implicated projects, or pin a newer build of one, and retry.
5. Record: an exclusion goes in `pack_manifest.json` `policy.exclusions` with a reason; a version pin goes through the cached version list, never a hand-edited lock.
6. Re-gate: run `python3 -m chaoslab verify`. A pack change that is not reproducible is not a fix.
